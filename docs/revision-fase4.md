##### tasks-corrupt-1 — confirmed / medium

DESC: useTasks() calls tasks.filter(...) on whatever JSON is stored under student-app:tasks, with no Array.isArray check. The confirm dialog is accepted, the page reloads and is blank, and it stays blank on every reload. ##### strict-shorts-inpage — confirmed / medium

```ts
const verdict = checkSite(nav.url, guard)
if (verdict.action === 'block') {
  const back = parseUrl(tab.src)

}
setTabs((prev) => prev.map((t) => (t.id === tabId ? nav.tab : t)))
```
The rest stays as it is: the toast-only path for 'warn'/'allow' distractions, and record/retitle for normal pages.

##### webview-file-1 — confirmed / low
TITLE: Code running in the app window can point a tab at file:// and read local files (webview src/loadURL bypasses the http/https guard)
FILE: desktop/src/guards.ts:192
DESC: The http/https restriction for tabs is only checked in will-attach-webview (on params.src at creation) and in will-frame-navigate (renderer-initiated navigations only). After a <webview> is attached, changing its src attribute or calling webview.loadURL() from the embedder makes the main process call guest.loadURL(). That is browser-initiated, so neither check runs, and the web-session onBeforeRequest filter only covers http/https. The embedder can then call webview.executeJavaScript() to read the page. The page already runs remote third-party code in its main world (https://www.youtube.com/iframe_api and the Spotify iFrame API are injected as <script> tags), and the CSP has no script-src. A compromised or malicious script from those origins, or any future XSS, would go from 'read localStorage' (same as the web version) to 'read the student's files' (SSH keys, documents…). SCENARIO: Script in the app window: `const v = document.querySelector('webview'); await v.loadURL('file:///home/<user>/.ssh/id_rsa'); await v.executeJavaScript('document.body.innerText')`. This returns the file contents, which can be exfiltrated with fetch().
VERIFIER: Mechanism reproduced: exp2-file.mjs with the secret path. From the app window's main world, v.loadURL('file://…/secret.txt') followed by executeJavaScript returned 'TOP-SECRET-1791220733'. setAttribute('src','file:///etc/hostname') returned 'vm'. The guest stayed in persist:lockin-web. That contradicts the README ('Solo direcciones http/https'). But it needs attacker code already running in app://lockin. FIX: desktop/src/sessions.ts configureSessions(): add webSession().protocol.handle('file', () => new Response('Bloqueado', { status: 403 })) so file:// cannot load in the tabs' partition however the navigation starts. Optionally add script-src 'self' https://www.youtube.com https://s.ytimg.com https://open.spotify.com (and a matching connect-src) to the CSP header set in desktop/src/main.ts:52.
